# Plan de distribution de la bêta HMP V2

**IMPORTANT** La candidate est `0.1.0-beta.1`. Rust, npm et Tauri utilisent le SemVer complet. Tauri lit la version du paquet npm et l’interface reprend cette valeur en l’absence d’IPC. Sur macOS, les champs Apple numériques valent `0.1.0` et `1`. L’identifiant Preview et le schéma de préférences sont conservés. Le scénario de mise à jour depuis une Preview installée reste à qualifier.

## macOS ARM64

**IMPORTANT** Le build candidat utilise `APPLE_SIGNING_IDENTITY=- npm run tauri -- build --ci --target aarch64-apple-darwin --bundles app -- --locked` depuis `v2/desktop`. Le DMG simple est créé avec `hdiutil create -format UDZO -srcfolder <dossier-contenant-le-bundle> -volname "HMP V2 0.1.0-beta.1" <dmg>`. Cette fabrication ne dépend pas de l’habillage Finder. Le plist et le Mach-O annoncent macOS 11.0. Vérifier avec `plutil`, `vtool -show-build`, `codesign --verify --deep --strict` et `hdiutil verify`.

**BLOCKER** La signature ad hoc protège l’intégrité du bundle et Gatekeeper peut rejeter le lancement normal d’un téléchargement. Après vérification de la provenance et du SHA-256, essayer l’ouverture. Si macOS affiche un blocage pour développeur non vérifié et que la politique du poste l’autorise, utiliser Réglages Système → Confidentialité et sécurité → Ouvrir quand même, puis confirmer pour cette seule application. Sur un Mac géré, le bouton peut être indisponible. Un blocage pour logiciel malveillant ou bundle altéré arrête l’essai. [Procédure Apple](https://support.apple.com/guide/mac-help/open-a-mac-app-from-an-unidentified-developer-mh40616/mac)

**BLOCKER** Tester le téléchargement en quarantaine et le cycle complet sur un compte standard. Copier le bundle dans `~/Applications`, vérifier lancement, destination, remplacement et désinstallation. Retirer le bundle pour désinstaller et documenter les préférences qui restent dans le profil, ainsi que les médias qui restent à destination. La qualification de la candidate se fait sans compte développeur ni notarisation. Une distribution Developer ID éventuelle reste une décision distincte. [Developer ID](https://developer.apple.com/developer-id/)

## Windows x64

**BLOCKER** Choisir NSIS par utilisateur (`currentUser`) pour un premier installateur dans `%LOCALAPPDATA%`. Préparer un essai sur Windows x64 depuis `v2/desktop` avec `npm run tauri -- build --ci --target x86_64-pc-windows-msvc --bundles nsis -- --locked`. La CI actuelle vérifie le binaire standard en debug sans bundle, et un binaire de qualification distinct exerce WebView2 natif. La qualification du NSIS exact utilise un compte local standard jetable, un chemin avec espaces et accents et le runtime préinstallé du runner. Le rapport JSON précise le résultat. Le cas sans runtime requiert un Windows x64 propre. [Installateur Windows Tauri](https://v2.tauri.app/distribute/windows-installer/)

**BLOCKER** Utiliser WebView2 Evergreen, déjà présent sur les postes concernés ou installé par le bootstrapper Microsoft. Sur poste propre et compte standard, vérifier le cas runtime présent, le cas absent, l’accès réseau requis et la réaction à une politique de poste restrictive. Vérifier la mise à jour manuelle avec la même identité, la désinstallation depuis Paramètres, les raccourcis et la conservation voulue des réglages et des médias. [Distribution WebView2](https://learn.microsoft.com/microsoft-edge/webview2/concepts/distribution)

**IMPORTANT** Préférer Authenticode avec horodatage pour l’exécutable et l’installateur publics quand une identité de signature approuvée est disponible. Un nouveau binaire signé peut déclencher SmartScreen. Sans signature, le risque d’avertissement ou de blocage dépend du poste. Vérifier `Get-AuthenticodeSignature` et le premier téléchargement sur un poste propre. Exiger une décision explicite sur le canal Windows avant de proposer un installateur sans signature. [SmartScreen et réputation](https://learn.microsoft.com/windows/apps/package-and-deploy/smartscreen-reputation)

**LATER** Réserver MSI/WiX à un besoin de déploiement administré. La première candidate utilise un seul format Windows pour limiter le nombre de parcours à qualifier.

## Formats d’icônes

**LATER** Un master carré RGBA de 1024 × 1024 px convient à une génération multi-plateforme après validation de l’identité. Le bundle macOS utilise un `.icns` avec tailles 16, 32, 128, 256 et 512 px et variantes Retina jusqu’à 1024 px. Windows utilise un `.ico` multirésolution incluant 16, 24, 32, 48, 64 et 256 px. Tauri accepte aussi le PNG carré de référence. Pour le social preview GitHub, préparer une image distincte PNG ou JPG sous 1 Mo, de préférence 1280 × 640 px. [Icônes Tauri](https://v2.tauri.app/develop/icons/) · [Aperçu social GitHub](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/customizing-your-repositorys-social-media-preview)

## Canal et vérification

**BLOCKER** Construire les deux packages du même SHA validé avec des dépendances verrouillées. Garder la fabrication et l’approbation séparées. Pour cette qualification, le job Windows reconnaît une ligne `HMP-BETA-RECIPIENT=age1…` dans la description de PR. Il utilise la clé publique pour chiffrer l’installateur, le rapport et son manifeste avant transfert via GitHub Actions. La clé privée et les packages déchiffrés restent locaux. Après validation humaine, la future préversion GitHub Releases peut servir les fichiers finaux et les notes. Le dépôt public permet la protection de branche et les checks GitHub Free. Les coûts de signature externes relèvent d’une décision séparée. Si l’identité Developer ID n’est pas disponible, poursuivre les essais internes ou documenter la compilation depuis les sources pour les contributeurs et différer le canal macOS public. [Branches protégées](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches) · [Gestion des releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)

**BLOCKER** Préparer par exemple `HMP-V2-0.1.0-beta.1-macos-arm64.dmg`, `HMP-V2-0.1.0-beta.1-windows-x64-setup.exe` et `SHA256SUMS.txt`. Inclure l’identifiant du commit, la provenance des builds, les notices et les notes de version. Après fabrication et signature, vérifier les fichiers téléchargés avec `shasum -a 256 -c SHA256SUMS.txt` sur macOS et `Get-FileHash -Algorithm SHA256` sur Windows. L’empreinte détecte un fichier modifié par rapport au manifeste publié. Les signatures de plateforme établissent l’identité de l’éditeur selon les règles locales. Les rapports de transfert V2 décrivent séparément l’intégrité de la copie média.
