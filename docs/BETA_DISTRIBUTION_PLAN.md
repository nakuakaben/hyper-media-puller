# Plan de distribution de la bêta HMP V2

**IMPORTANT** Proposer `0.2.0-beta.1`. Lors d’un lot de préparation distinct, aligner la version de l’interface, la configuration Tauri et les métadonnées des paquets sur la version publique. Vérifier la représentation numérique de la version chez NSIS et macOS, ainsi que l’ordre de mise à jour entre deux bêtas et la version stable. Conserver l’identifiant Preview pour éviter une migration involontaire des réglages, sous réserve d’un test Preview → bêta et de la coexistence avec Electron V1.

## macOS ARM64

**BLOCKER** Choisir un DMG qui contient le `.app` ARM64. Sur macOS, la configuration actuelle cible déjà `app`. Pour un essai local, construire dans `v2/desktop` avec les dépendances installées par `npm ci`, puis `npm run tauri -- build --ci --target aarch64-apple-darwin --bundles app,dmg -- --locked`. Vérifier l’architecture avec `file` ou `lipo -archs`, la version et le bundle identifier avec `plutil`, et comparer le minimum de macOS dans le plist et le Mach-O avec `vtool -show-build`. Le build d’audit annonce 10.13 dans le plist et 11.0 dans le binaire. Fixer un minimum cohérent et qualifié sur un Mac ARM64. [Distribution DMG Tauri](https://v2.tauri.app/distribute/dmg/)

**BLOCKER** La distribution publique proposée passe par Developer ID Application, le runtime renforcé, la notarisation Apple puis l’agrafage du ticket au produit distribué. Obtenir un certificat Developer ID et utiliser le service de notarisation requièrent une adhésion Apple Developer Program. Apple indique 99 USD par an au tarif de référence, avec variation locale et dispenses possibles. La compilation et le packaging local peuvent être testés sans adhésion. Aucun achat ni compte n’est nécessaire à cet audit. [Apple Developer Program](https://developer.apple.com/programs/enroll/) · [Developer ID](https://developer.apple.com/developer-id/) · [Signature Tauri](https://v2.tauri.app/distribute/sign/macos/)

**BLOCKER** Sur un Mac ARM64 de test avec un compte standard, télécharger le DMG via un navigateur, vérifier le ticket et la signature avec `xcrun stapler validate` et `codesign --verify --deep --strict`, puis contrôler la décision Gatekeeper avec `spctl` sur l’application et tester son ouverture. Copier le bundle vers `~/Applications` et tester le lancement, le dossier destination et le remplacement par une candidate ultérieure. Désinstaller en retirant le bundle et documenter les préférences utilisateur qui persistent. Préserver les médias copiés lors de ces opérations.

## Windows x64

**BLOCKER** Choisir NSIS par utilisateur (`currentUser`) pour un premier installateur dans `%LOCALAPPDATA%`. Préparer un essai sur Windows x64 depuis `v2/desktop` avec `npm run tauri -- build --ci --target x86_64-pc-windows-msvc --bundles nsis -- --locked`. La CI actuelle vérifie le binaire standard en debug sans bundle, et un binaire de qualification distinct exerce WebView2 natif. L’installation per-user de la candidate reste à vérifier sur compte standard. [Installateur Windows Tauri](https://v2.tauri.app/distribute/windows-installer/)

**BLOCKER** Utiliser WebView2 Evergreen, déjà présent sur les postes concernés ou installé par le bootstrapper Microsoft. Sur poste propre et compte standard, vérifier le cas runtime présent, le cas absent, l’accès réseau requis et la réaction à une politique de poste restrictive. Vérifier la mise à jour manuelle avec la même identité, la désinstallation depuis Paramètres, les raccourcis et la conservation voulue des réglages et des médias. [Distribution WebView2](https://learn.microsoft.com/microsoft-edge/webview2/concepts/distribution)

**IMPORTANT** Préférer Authenticode avec horodatage pour l’exécutable et l’installateur publics quand une identité de signature approuvée est disponible. Un nouveau binaire signé peut déclencher SmartScreen. Sans signature, le risque d’avertissement ou de blocage dépend du poste. Vérifier `Get-AuthenticodeSignature` et le premier téléchargement sur un poste propre. Exiger une décision explicite sur le canal Windows avant de proposer un installateur sans signature. [SmartScreen et réputation](https://learn.microsoft.com/windows/apps/package-and-deploy/smartscreen-reputation)

**LATER** Réserver MSI/WiX à un besoin de déploiement administré. La première candidate utilise un seul format Windows pour limiter le nombre de parcours à qualifier.

## Formats d’icônes

**LATER** Un master carré RGBA de 1024 × 1024 px convient à une génération multi-plateforme après validation de l’identité. Le bundle macOS utilise un `.icns` avec tailles 16, 32, 128, 256 et 512 px et variantes Retina jusqu’à 1024 px. Windows utilise un `.ico` multirésolution incluant 16, 24, 32, 48, 64 et 256 px. Tauri accepte aussi le PNG carré de référence. Pour le social preview GitHub, préparer une image distincte PNG ou JPG sous 1 Mo, de préférence 1280 × 640 px. [Icônes Tauri](https://v2.tauri.app/develop/icons/) · [Aperçu social GitHub](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/customizing-your-repositorys-social-media-preview)

## Canal et vérification

**BLOCKER** Construire les deux packages du même SHA validé avec des dépendances verrouillées. Garder la fabrication et l’approbation séparées. Une future exécution manuelle sur runners GitHub standard peut compiler, tester et déposer des artefacts de vérification avec droits de lecture sur le dépôt. Après validation humaine, la future préversion GitHub Releases peut servir les fichiers finaux et les notes. Le dépôt public permet la protection de branche et les checks GitHub Free. Les coûts de signature externes relèvent d’une décision séparée. Si l’identité Developer ID n’est pas disponible, poursuivre les essais internes ou documenter la compilation depuis les sources pour les contributeurs et différer le canal macOS public. [Branches protégées](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches) · [Gestion des releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)

**BLOCKER** Préparer par exemple `HMP-V2-0.2.0-beta.1-macos-arm64.dmg`, `HMP-V2-0.2.0-beta.1-windows-x64-setup.exe` et `SHA256SUMS.txt`. Inclure l’identifiant du commit, la provenance des builds, les notices et les notes de version. Après fabrication et signature, vérifier les fichiers téléchargés avec `shasum -a 256 -c SHA256SUMS.txt` sur macOS et `Get-FileHash -Algorithm SHA256` sur Windows. L’empreinte détecte un fichier modifié par rapport au manifeste publié. Les signatures de plateforme établissent l’identité de l’éditeur selon les règles locales. Les rapports de transfert V2 décrivent séparément l’intégrité de la copie média.
